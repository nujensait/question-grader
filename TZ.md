# Техническое задание: Разработка LLM-грейдера для экзаменационных вопросов

## 1. Введение

### 1.1. Название проекта
Разработка Artisan-команды `grade:questions` для оценки качества экзаменационных вопросов с использованием LLM.

### 1.2. Цель
Создать надежный и воспроизводимый механизм автоматической оценки набора из 60 экзаменационных вопросов (SPHR, AWS и др.) по шкале от 1 до 10. Оценка должна выполняться на основе заранее определенных критериев качества, которые интерпретируются и применяются LLM.

### 1.3. Исходные данные
- **Входной файл:** `questions.json`, расположенный в корне проекта.
- **Структура файла:** JSON-массив объектов. Каждый объект содержит поля:
    - `id` (string) — уникальный идентификатор вопроса.
    - `question` (string) — текст вопроса.
    - `answer` (string) — правильный ответ.
    - `distractors` (array of strings) — массив из 4 неправильных вариантов ответа.
    - `explanation` (string) — объяснение правильного ответа.
- **Количество вопросов:** 60.

### 1.4. Целевой результат
- **Выходной файл:** `grades.json`, расположенный в корне проекта.
- **Структура файла:** JSON-объект с единственным ключом `results`, содержащим объект, где ключи — это `id` вопросов, а значения — целые числа (оценки) от 1 до 10.
- **Пример:**
```json
{
  "results": {
    "q_acb7e7": 8,
    "q_9d41de": 2
  }
}
```
- **Критерии качества вывода:**
    - В объекте `results` должны присутствовать все 60 `id` ровно один раз.
    - Все значения должны быть целыми числами в диапазоне `[1, 10]`.

## 2. Функциональные требования

### 2.1. Artisan-команда
- Разработать Artisan-команду `grade:questions`.
- При выполнении команда должна:
    1.  Прочитать и декодировать файл `questions.json`.
    2.  Для каждого вопроса из массива получить оценку качества от LLM.
    3.  Сохранить все оценки в файл `grades.json` в указанном формате.
- **Вывод в консоль (`stdout`):** Команда не должна выводить в `stdout` никакой информации, кроме стандартных сообщений Laravel (например, при ошибках), но при штатной работе вывод должен быть минимальным. Основной результат — файл `grades.json`.

### 2.2. Процесс оценки вопроса
- Для каждого вопроса необходимо отправить запрос к LLM (модель `gpt-5.5`).
- Промпт должен содержать текст вопроса, правильный ответ, все дистракторы и объяснение.
- В промпте должны быть четко определены **четыре критерия оценки**, по которым LLM должен анализировать вопрос:
    1.  **Содержательная корректность (Content Validity):** Насколько вопрос проверяет важное, значимое знание, а не тривиальный факт.
    2.  **Четкость конструкции (Construct Clarity):** Насколько ясна и однозначна формулировка вопроса. Исключает ли она двусмысленность?
    3.  **Качество дистракторов (Distractor Quality):** Насколько правдоподобны и однородны неправильные ответы. Есть ли среди них "смешные" или очевидно неверные? Есть ли два правильных ответа?
    4.  **Полезность объяснения (Explanation Usefulness):** Насколько хорошо объяснение раскрывает причину правильности ответа и неправильности дистракторов, а не просто перефразирует вопрос.
- **Формат ответа LLM:** Ответ должен быть строго в JSON-формате.
    ```json
    {
      "content_validity": 8,
      "construct_clarity": 9,
      "distractor_quality": 7,
      "explanation_quality": 8,
      "final_grade": 8
    }
    ```
- **Вычисление финальной оценки:** `final_grade` в ответе LLM должен быть целым числом от 1 до 10. Ожидается, что LLM вычислит его как среднее арифметическое (или иным способом) на основе четырех критериев. Приложение должно извлечь именно это значение.

### 2.3. Надежность и обработка ошибок
- **Ретраи (Retries):** В случае ошибки от LLM (таймаут, 5xx ошибка, невалидный JSON в ответе), приложение должно повторять запрос до 3 раз с экспоненциальной задержкой (например, 1, 2, 4 секунды).
- **Некорректный ответ LLM:** Если после всех ретраев LLM возвращает ответ, который невозможно распарсить (отсутствует поле `final_grade`, значение вне диапазона `1..10`), команда должна присвоить этому вопросу оценку `1` и записать ее.
- **Исключительные ситуации:** Если весь процесс падает с критической ошибкой (например, не читается `questions.json`), команда должна завершиться с кодом ошибки `1`. В остальных случаях, даже если какой-то вопрос не удалось оценить, программа должна завершиться успешно (`0`), записав для проблемного вопроса оценку по умолчанию (`1`).
- **Кеширование (Опционально, но рекомендуется):** Для предотвращения повторной отправки запросов при перезапусках, приложение должно кешировать уже полученные оценки. Ключом кеша может быть `id` вопроса. Хранилище — на усмотрение разработчика (файл, Redis, база данных). Если оценка для `id` уже есть в кеше, она должна использоваться, а новый запрос к LLM не отправляться. Результат в `grades.json` должен формироваться из данных кеша.

## 3. Нефункциональные требования

- **Среда выполнения:** Laravel (версия 10 или 11).
- **Язык:** PHP 8.1+.
- **Зависимости:** Для работы с LLM требуется HTTP-клиент (Guzzle). Подключение к OpenAI API осуществляется через официальный SDK или кастомный клиент.
- **Код:** Должен следовать принципам SOLID и PSR. Основная логика должна быть вынесена из команды в сервис-классы (например, `QuestionGraderService`, `LlmClient`, `PromptBuilder`).
- **Тестируемость:** Код должен быть написан так, чтобы его можно было легко тестировать (использовать Dependency Injection, интерфейсы).
- **Документация:** Код должен содержать комментарии на русском или английском языке для пояснения ключевых моментов.

## 4. Требования к реализации (Критерии приемки)

1.  При выполнении `php artisan grade:questions` в корневой папке проекта создается или перезаписывается файл `grades.json`.
2.  Файл `grades.json` содержит 60 записей, каждая из которых соответствует `id` из `questions.json`.
3.  Ни один из `id` не пропущен.
4.  Все оценки — целые числа от 1 до 10.
5.  При повторном запуске команды для тех вопросов, для которых уже есть оценки, новые запросы к OpenAI не отправляются (если реализовано кеширование).
6.  В случае проблем с LLM (3 неудачные попытки) для вопроса записывается оценка `1`, и выполнение продолжается.
7.  `stdout` содержит только информационные сообщения от команды, но не содержит "мусора" из JSON-ответов LLM.

## 5. Примерный алгоритм работы команды

```
Начало выполнения команды
|
V
Прочитать вопросы из questions.json
|
V
Для каждого вопроса из questions.json:
|   |
|   V
|   Проверить кеш: есть ли оценка для этого id?
|   |
|   +--Да--> Взять оценку из кеша
|   |
|   +--Нет--> 
|       |
|       V
|       Для attempt от 1 до 3:
|       |   |
|       |   V
|       |   Сформировать промпт с вопросом и критериями
|       |   Отправить запрос к gpt-5.5
|       |   |
|       |   +--Успешно и валидный JSON с final_grade--> Сохранить в кеш и прервать цикл ретраев
|       |   |
|       |   +--Ошибка или невалидный JSON--> Увеличить задержку и повторить
|       |
|       V
|       Если после 3 попыток успеха нет -> записать в кеш оценку 1
|
V
Сформировать массив results: [id вопроса => оценка] для всех 60 вопросов
|
V
Записать массив в файл grades.json
|
V
Конец выполнения команды
```

## 6. Критерии качества кода

- **Читаемость:** код легко читается, переменные названы осмысленно.
- **Модульность:** ответственность разделена между классами.
- **Устойчивость к ошибкам:** приложение не падает целиком из-за одного упавшего запроса.
- **Управляемость:** промпты и критерии оценки легко изменять в одном месте.
